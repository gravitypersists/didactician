§ 2s-02

The pipeline, one stage at a time

whole first → step-through · B1o-1

The whole pipeline as one picture, then each stage opened with the file it produces. Stages are not agents (H-21).

Step 0 (draft): "Your main session is the orchestrator. It runs eight stages in order and moves each stage's files on to the next. Most stages are done by a fresh subagent; one is a script, and one is you."

  • 1 Intake: the orchestrator turns your request into brief.md: audience, time, objectives.
  • 2 Research: a fresh researcher agent collects the facts and sources the rest of the pipeline works from.
  • 3 Plan: the instructional designer writes a learning plan, a wireframe mockup and a cut list.
  • 4 You approve: always. Approve, revise or rescope before anything is built.
  • 5 Build: a page builder, plus a fresh builder agent for each complex widget, like the diagram you're looking at.
  • 6 Gate: a Playwright script renders the page at 360, 768 and 1280px and fails it on overflow, broken arrows, console errors…
  • 7 Review: two reviewers, one for accuracy and one for teaching and UX, each in a fresh context.
  • 8 Deliver: a site/ folder for any static host, plus a log.md of everything that happened.

§ 3s-03

Why it's built this way

predict → 3 overlays · B1o-2

Each structural choice prevents a failure the reader knows from their own agent work. Confront "self-review is enough".

Problem 1 · Predict · k-01
The page is built. Before it ships, which check would you trust most to catch a claim it got subtly wrong?
  1. A) Ask the builder to re-read its page and double-check its claims. (tempting)
  2. B) A fresh reviewer that sees only the brief, the page and the fact base, not the builder's reasoning.
  3. C) The Playwright gate: if it passes, the page is fine.
Solution. B. The builder knows what it meant and reads that intent back into the text; LLM judges have been found to rate their own outputs higher than human annotators do (GPT-4, Llama 2). C checks only what a machine can check. Didactician runs C, then B. Whether that split beats one agent reviewing itself hasn't been measured; it's a hypothesis the design still has to test.
  • Rule 1 · The orchestrator coordinates, never authors. Your main session is your point of contact: it dispatches agents and records what they return. It never writes the page or judges it, so the reviewer and the author are never the same context.
  • Rule 2 · Agents communicate only through files. Each agent gets a handoff prompt in and returns a report out, in a fixed format. Agents never talk to each other. Every prompt and report is kept, so a run can be audited and resumed.
  • Rule 3 · You approve the plan before anything expensive. Checking the plan early is part of the design: a wrong premise caught here can't cascade through the build, the gate and the review, which saves the time and tokens of every later stage.

Dropped (H-23, designer's call): "scripts gate what's checkable". The Gate stage and Problem 1's option C already show a machine checking rendering but not truth; the useful consequence, round caps that bound token spend, is one clause in § 6.

§ 4s-04

The idea underneath: cognitive load

example → rule → contrast · B4o-3

Just enough theory to predict whether a design choice adds or removes load for a given reader.

Opening (your wording, H-25): "Look at this expression: total = sum(x for x in values if x > 0). A non-programmer must track about ten separate tokens (total, =, sum, x, for, in, values, if, >, 0), look up what each means, and work out how each connects to the next. An experienced developer reads it at a glance as one familiar pattern: sum the positive numbers. The code doesn't change. For the novice, tracing the syntax uses up working memory before they even work out what the line does. For the developer, long-term memory compresses the whole line into one chunk, leaving room to think about edge cases."

  • New information passes through a working memory that is limited in capacity and duration. What's already in long-term memory comes back as a chunk, and the limit stops applying to it. (No number is given; the research behind this page doesn't support one.)
  • Intrinsic load: how many elements of the material must be held together, relative to what you already know. Only sequencing changes it.
  • Extraneous load: effort spent on the presentation rather than the content. This is the part design controls.
  • "Here is extraneous load you can feel: do the same lookup in both versions of Diagram III."

The collapsed germane-load note is cut (H-28).

Problem 2 · Predict · k-02
Suppose this page stopped to explain, step by step, what a subagent is. Reader 1 has never used an AI coding agent. Reader 2 writes subagents every day. What happens to each reader's cognitive load?
  1. A) Lower for both: more explanation always makes things easier. (tempting)
  2. B) Lower for Reader 1, higher for Reader 2.
  3. C) Higher for both: it's extra paragraphs to read.
Solution. B. It's the code line again. For Reader 2, "subagent" is already one chunk; walking through it gives them nothing new, but they still read it and check it against what they know, which is extraneous load. For Reader 1 the same paragraphs build the chunk they lack. Guidance that helps a novice can get in an expert's way (the expertise reversal effect). That's why Didactician fixes one audience per page, and why this page names subagents without explaining them.

Problem 3 · Apply · k-05
You want to teach new backend developers what happens during a TCP connection handshake: a fixed sequence of messages, each depending on the last. Which building block should carry it?
  1. A) A sandbox with sliders for every parameter, so there's lots to explore. (tempting)
  2. B) A step-through, one message at a time, with a prediction before the step that surprises people.
  3. C) A multiple-choice quiz at the end of a page of prose.
Solution. B. A fixed sequence is a process, and a process maps onto a step-through: one change per step, the rest dimmed. A prediction at the surprising step makes it Constructive rather than just clicking "next". A is tempting because it's the most interactive, but more controls are more elements to hold, and a sandbox suits a system you explore, not a sequence you follow: interactive isn't the same as effective. C checks recall afterwards but leaves the hard part to prose.
w-blocks · 7 specimen cards complexity high A 2-column grid (one column on mobile). Each card: "Specimen N · Name", a working example, and one line on what it does for load. All examples reuse the § 4 expression (values = [3, -1, 4, 0]) or the pipeline.
  1. Progressive reveal: "▸ Show what's in a handoff prompt" opens 4 lines (role, task, inputs, outputs). Optional depth stays out of your working memory until you ask; never hide what every reader needs.
  2. Multiple choice: "Which does a reviewer never see?" the brief / the page / the builder's report ✓. Recalling beats rereading; the explanation of the wrong answer is the payoff.
  3. Predict, then reveal: "What is total?" 6 / 7 ✓ / 8; the reveal shows -1 and 0 filtered out. Committing first means a wrong guess surprises you, and surprise sticks.
  4. Think, then reveal: "Why might the agent that wrote a page miss its own mistakes?" [Show a model answer]; no text box. You generate the answer in your head; no typing.
  5. Step-through: the expression in 3 steps, ‹ 2 of 3 ›: filter → sum → assign; the active part highlighted. One change at a time; Diagrams I–II are the full-size version.
  6. Contrasting cases: two tiny line charts, legend vs. labels on the lines, "Which series is higher in March?" Two cases differing in one feature show what matters; Diagram III is the full-size version.
  7. Sandbox, prediction first: a slider for t in if x > t (0…5), total updating live; "Before you drag: as t rises, when does total first drop below 7?" (t = 3). Dragging alone is Active; predicting first makes it Constructive.
Every disclosure shows an arrow and an action label (H-27); reveals appear in place; 44px targets; nothing hover-only.
