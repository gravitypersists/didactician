# h0-3 · W-02 (w-sizing-sandbox) and the text

Model runs: `SizingModel.evaluate(SizingData, {storefront, orders, dispatch[, payments]}, spare)` in Node, loading `data.js` and `model.js` from `inputs/ch05-r0/site/widgets/w-sizing-sandbox/`. Notation below: `(sf, or, di)` = memory request per copy in GB; "off"/"on" = spare switch. `selftest.mjs` passes.

1. **k-09 (answer), pointer to W-02.** Quote: "try `orders` at 8 and then 12 GB in W-02". What's wrong: from any state the text has led the reader to, nothing happens. Raising `orders` to 8 and then to 12 never changes the node count, so the promised "another node on the bill" can't be seen. The count only moves if storefront and dispatch are first set to 2.5 and 1.5, which the page never mentions (those values appear only in the mount contract comment). Evidence: defaults (4, *, 2), off: orders 6, 8, 12 and 13 → 4, 4, 4, 4. On: → 5, 5, 5, 5. At-use state from the first "thing to notice" (2, *, 1), off: orders 5.5, 8, 12 → 3, 3, 3. On: → 4, 4, 4. Only (2.5, 8, 1.5) → 3 and (2.5, 12, 1.5) → 4, with the spare off.

2. **k-04 (feedback for C), pointer to W-02.** Quote: "on a full cluster that's another node, or a Pod that waits. W-02, below, shows how far it goes." What's wrong: k-04 is about doubling the `payments` request, but W-02 has no `payments` control. Only storefront, orders and dispatch are adjustable (`data.js`: only those three have `adjustable`; `ORDER` lists just them), and the caption confirms that payments "stay[s] as the teams set" it. The reader can't do what the check sends them to do. Even if they could, the model shows no extra node. Evidence: `{payments: 4}` added to the defaults → 4 nodes off and 5 on, the same as with payments at 2.

3. **s-04, first "thing to notice".** Quote: "Set each request to what that service used at the rush." What's wrong: (a) The reader can set only three of the five services. Payments and notifications reserve 2 GB and used 0.5 GB, but they stay at 2. (b) Only memory requests can change, and the widget never shows processor use (`useCpu` is "shown nowhere", per the data.js header). So "each request" can't mean processor requests, even though the answer W-02 gives is "set by processor". The bullet doesn't say "memory request". Evidence: (2, 5.5, 1), off → 3 nodes, setBy `processor`, memOnly 2, cpuOnly 3. Processor requests stay at 1 core per dispatch Pod, against 0.6 used.

4. **s-04, first "thing to notice" → no debrief.** Quote: "what sets that number?" What's wrong: W-02's answer is "Processor", which is the central surprise of the exercise, and no prose after the widget mentions it. Nothing explains that once memory is right-sized, the dispatch Pods' processor requests (6 × 1 core = 6 of 3 × 3.9 cores) set the count, or that the reader can't lower them here. The following paragraphs talk only about bin packing, the idle bar and billing. Evidence: as in 3. `grep` of the s-04 prose after the mount finds no "processor".

5. **s-04 lead paragraph / the SET BY readout.** Quote: "what sets that number?". What's wrong: the text never introduces the SET BY readout, and the readout's value "Both" means two different things. Model `setByWord` returns `'both'` when memory alone and processor alone each reach the count, and also when only the two together do (code comment: "both alone reach it, or only the two together do"). The sub-line helps, but no text tells the reader how to read "Both". Evidence: (2, 8, 1), off → `both` with memOnly 3 and cpuOnly 3, where each resource alone forces 3. The selftest's (2.5, 6, 1.5) → `both`, which is labelled the same way.

6. **s-04, third "thing to notice".** Quote: "Push `orders` past 13 GB." What's wrong: unlike the other two bullets, it asks no question and says nothing about what to look for. The s-04 prose after the widget never comes back to it. The explanation arrives only two sections later, in s-06 ("W-02 shows it when you push `orders` past 13 GB"). Evidence: (4, 13.5, 2), on → nodes null, never `[orders 13.5]`. The widget shows NODES "—", a never-placeable bar and a warning, but the s-04 text gives the reader no way to interpret them.

7. **s-04 final paragraph vs W-02's default state.** Quote: "Fennel rents two extra nodes because on Friday the teams' padded requests had filled three nodes on paper … Next, node 06 has stayed nearly empty … a node's worth of spare room". What's wrong: W-02, which this section builds on, puts one extra node down to padding and the other to the spare. The paragraph puts both extra nodes down to padding first, then calls one of them spare. Evidence: at use (2, 5.5, 1), off → 3. Defaults (4, 6, 2), off → 4 (+1 from padding). On → 5 (+1 spare). The NODES sub-line itself says "4 for the Pods + 1 spare".

8. **k-05 vs s-04 final paragraph vs W-02 drawing.** Quote (k-05): "nodes 05 and 06 are still nearly empty". Quote (final paragraph): "node 06 has stayed nearly empty since Friday". What's wrong: the text contradicts itself on how many of the new nodes are nearly empty, and W-02's default drawing matches neither framing. It shows two nearly empty nodes: node 4 holds a single notifications Pod, and node 5 is the empty spare. That invites the reader to map W-02's nodes 4 and 5 onto the story's 05 and 06, which the text doesn't intend. Evidence: defaults, on → placement `[[or1,sf1,di1],[sf2,sf3,di2,di3],[di4,di5,di6,pa1,pa2,no1],[no2],[]]`.

9. **Node names: widget vs story.** Quote (s-04/k-05): "nodes 05 and 06"; widget readout: "NODES 05". What's wrong: the story names nodes 01, 02, 04, 05 and 06. W-02 numbers its drawn nodes 1…n (`snapshot`: `String(i + 1)`, label "NODE · 1"), but zero-pads the count (`pad2`), so the count reads "05", the same form as the story's node *name* "05". No text says that W-02's nodes are a hypothetical repacking that doesn't correspond to 01–06. Evidence: `index.js` `rNodes.val.textContent = pad2(ev.nodes)` versus the `snapshot()` node ids.

10. **s-04 idle-bar paragraph and final paragraph vs W-02's "rented room".** Quote: "W-02's idle bar splits the room Fennel rents but doesn't use into two kinds" / "on every node about 3 GB of the 16 GB machine is kept back for the system … and Fennel pays for it anyway". What's wrong: W-02 counts rented room at 13 GB per node, and its NODES sub-label says "what Fennel rents, and pays for". So the system-reserved 3 GB per node, which the final paragraph names as the third thing Fennel pays for, is invisible in the bar. "RESERVED 38 OF 65 GB" understates what is rented (5 × 16 = 80 GB). Evidence: defaults, on → rented 65, idle `{used 19.5, reservedUnused 18.5, notReserved 27}`, which sums to 65. `CAPACITY.memory = 13`.

11. **s-04 idle-bar paragraph.** Quote: "The 'less than a third busy' on Ari's dashboard counts both kinds together." What's wrong: the sentence implies that W-02's bar is what the dashboard shows. W-02's 30% comes from a repacked 65 GB denominator that leaves out the system share. Measured against the 80 GB actually rented, the same use is 24%. The match to "less than a third" holds only by leaving the system share out (see 10). Evidence: defaults, on → used 19.5 / rented 65 = 30%. 19.5 / 80 = 24%.

12. **s-04 lead / s-05, the spare switch: what it can show.** Quote (bullet 2): "Switch off the spare node. What does insurance cost?" Quote (s-05): "the spare-node switch in W-02 shows what it costs". What's wrong: the spare is always exactly one empty node added on top (`nodes = base + (spare ? 1 : 0)`). So the switch's answer is "one node (13 GB)" in every state, and there is nothing to explore or compare. With no money shown, "what it costs" can only be answered in nodes, and the text doesn't say so. Evidence: every model run above has on = off + 1: (4, 6, 2) 5/4, (2, 5.5, 1) 4/3, (4, 13, 2) 5/4.

13. **Naming: the switch.** Quote (s-05): "the spare-node switch in W-02". Widget control label: "Keep room to lose a node". What's wrong: the text and the widget call the same control by different names. The text never quotes the widget's label, though the live sentence says "Spare node on/off". Evidence: `data.js` `SHEET.spare = 'Keep room to lose a node'`, `liveSpare: 'Spare node {state}. '`.

14. **Naming: the idle bar.** Quote: "W-02's idle bar". What's wrong: the widget never uses the word "idle". Its heading is "The rented room", with segments "Used at the rush", "Reserved, not used" and "Not reserved". The text's two kinds ("room that no Pod has reserved", "room that Pods have reserved and don't use") need translating onto those labels. Evidence: `data.js` `SHEET.idle.head = 'The rented room'`.

15. **Naming: processor vs CPU.** The page says "processor" throughout, and the widget's readout says "SET BY · PROCESSOR". The node footers and the drawing strings say "CPU" (`STRINGS.cpu: 'CPU'`), so a reader answering "what sets that number?" sees two words for one resource inside W-02. The lead paragraph never mentions the processor footers at all.

16. **s-04 lead paragraph, what the drawing shows.** Quote: "Each Pod's outline is what it reserves, and the solid fill inside it is what it used at last Friday's rush." What's wrong: the text doesn't say what happens when a request drops below use. Evidence: (1.5, 6, 2), on → over `[storefront]`. `cluster.js` `drawPod` adds `.wc-over` when use > size.

18. **s-04 lead paragraph: which Pods are counted.** Quote: "It opens on Fennel's requests as the teams set them".
