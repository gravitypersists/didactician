§ 02 What the scheduler counts

In Chapter 4’s drawings, every Pod had a size, every node had room for six units, and the scheduler looked for “a node with room”. Kubernetes didn’t measure those sizes, though. Each team wrote them into its service’s manifest when Fennel moved, saying how much memory and how much processor each copy of the service should have set aside for it. Fig. 01 shows the part of storefront’s manifest that does this. Engineers call these numbers the Pod’s requests. One unit of room in Chapter 4 stood for 2 GB of memory request, so storefront’s two units are the 4 GB in Fig. 01.

New term · 01 / 04

requests

The memory and processor a Pod reserves on its node, written in its manifest. The scheduler places Pods by their requests, never by what they use.

memory and processor, counted separately

Chapter 4’s “room”, written down.

Each node, in turn, offers a fixed amount of both. Fennel’s nodes are rented machines with 16 GB of memory and 4 processor cores each. Part of every machine is kept back for its operating system and for Kubernetes’ own programs, so the Pods on a node can reserve only about 13 GB of memory and 3.9 cores between them.

Why can Pods reserve only about 13 GB of a 16 GB node?

Every machine runs its own operating system and Kubernetes’ own programs, such as the node agent, and they need memory and processor too. So part of each node is kept back for them, and the scheduler counts only the rest, which engineers call the node’s allocatable room. On one provider, for example, a 16 GB node keeps back about 2.7 GB of memory but less than a tenth of a core, which is roughly where Fennel’s 13 GB and 3.9 cores come from. Small machines lose a bigger share: on the same provider, a 4 GB node keeps back about a quarter of its memory. Other providers publish their own numbers.

Memory and processor are counted separately, and a Pod fits on a node only if both of its requests fit into what that node still has unreserved. Chapter 3 promised that the two would be counted separately, and Fig. 02 shows why it matters: a node can have plenty of memory left while its processor is nearly all reserved, and then a new dispatch Pod doesn’t fit there, however much memory is free.

The loop that makes this check is the scheduler, the part of Kubernetes that gives each new Pod a node. It works in two steps. First, it rules out every node that doesn’t have room for the Pod’s requests. Then it scores the nodes that are left and picks the one with the best score, choosing at random if two are tied. With default settings, the score mainly rewards the node with the most room left unreserved. The scheduler also prefers, by default, to spread copies of the same service across different nodes, but only as a preference: if it can’t spread them, it places them anyway.

That’s why, on moving day in Chapter 4, storefront’s three Pods went to three different nodes. Nodes 01 and 04 had the most room left, so the first Pod went to one of them and the second to the other. The third went to node 02, which had no storefront copy yet and more room than node 03. Notice what the scheduler wasn’t trying to do: fit Fennel onto as few nodes as possible.

Teams can also add placement rules of their own, such as keeping a service’s copies on different nodes, sending some Pods only to particular machines, or keeping ordinary work off special ones; your engineers will tune these.

PREDICTCheck 02 / 09

On a quiet Tuesday morning, Ari’s dashboard shows node 02 at 15% busy. The Pods already on it have reserved all but 1 GB of its memory. A new Pod requests 2 GB. Will the scheduler put it on node 02?

The scheduler never looks at how busy a node is. When it checks for room, it counts what the Pods on each node have reserved, not what they are using. The Kubernetes documentation says the scheduler refuses a node whose reservations are full “although actual memory or CPU resource usage on nodes is very low”, and it gives the reason: the room is protected for when “resource usage later increases, for example, during a daily peak in request rate.” A reservation is a promise to the Pod, and the scheduler keeps it even while the Pod isn’t using the room.

ANALOGYYou know this from budgeting. Think of each node as a department’s budget, each request as the budget a project reserves, and the scheduler as finance, which approves a new project only in a department whose reservations still leave room for it. Whether the projects have actually spent their money doesn’t come into it.

WHERE THIS ANALOGY BREAKSA finance team would notice a department sitting on unspent money and move it to where it’s needed. The scheduler never does: reserved room that a Pod isn’t using stays reserved, at 3 a.m. as at the dinner rush, and no other Pod can be placed in it.

In Chapter 4’s terms, the scheduler is one implementation of the reconcile loop, and you can now fill in its loop lens completely. It wants every Pod on a node with room for its requests. It sees Pods that have no node, and how much memory and processor each node has left unreserved. What it does about a gap is rule out the nodes that are too full, pick the emptiest of the rest, and write that node into the Pod’s record. That leaves one question for the next section: what happens when no node passes the first step?

For most of that hour, the third dispatch copy was pending, and Pending is the word Ari’s dashboard showed for it.

New term · 02 / 04

pending

A Pod the scheduler hasn’t been able to place yet. It waits, and the scheduler keeps trying and records why.

Not failed, and not fixed by waiting alone.

Each time the scheduler fails to place a Pod, it records why. On Friday the line read 0/3 nodes are available: 2 Insufficient cpu, 3 Insufficient memory., which is in the format engineers see, though the exact wording varies between Kubernetes versions. Read it from left to right. “0/3 nodes are available” means that none of the three nodes passed the first step. The rest counts what each node was short of: all three lacked 2 GB of free memory, and two of them, 01 and 02, also lacked a whole free core. So the line already answers the first question to ask about a pending Pod: what is short, and where?

Notice what the line doesn’t say, which is that the cluster was full. Between them, the three nodes had 3 GB of memory free, more than the Pod’s 2 GB, and about 3 cores. But the memory came in pieces of 1 GB, one on each node, and a Pod runs on one node, so the pieces never add up: both of its numbers have to fit on the same node. Chapter 3 kept its drawings clear of this case on purpose, but on a real cluster it’s common. It matters to Morgan, too, because those leftover pieces on 01, 02 and 04 are room Fennel pays for that no Pod of this size can use.

There are two wrong ways to read Pending. It isn’t a failure: nobody has to resubmit anything, because the scheduler keeps trying and places the Pod as soon as a node has room for it. But it isn’t harmless either, because in Fennel’s cluster no loop makes room by itself. Someone has to add a node or free some room, as Ari’s team did at about 18:40. (Chapter 8 introduces a loop that can add nodes.) When a Pod is pending, these are the questions to ask:

  • “What’s short, and on how many nodes?”
  • “Is it short because demand really grew, or because what we reserved is more than we use?”

The second question leads straight to Morgan’s bill.

Is “pending” always about room?

No. Pending also covers the time a Pod that already has a node spends downloading its image before it can start, as in Chapter 4. The scheduler’s recorded reason tells the two apart: a Pod waiting for room has one, and a Pod that is downloading its image already has a node.

§ 04 What Morgan pays for

In the provider’s standard mode, which is the one Fennel uses, the bill counts machines. Fennel pays for each node for as long as it exists, whether the room on it is reserved, used or empty. So Morgan’s five nodes are the bill, and there are five because of the requests: on Friday, three nodes couldn’t hold everything the teams had reserved, so Ari’s team rented two more.

PREDICTCheck 05 / 09

A month on, nodes 05 and 06 are still nearly empty. With default settings, what does Kubernetes do about them?

Fitting Pods’ reservations onto as few nodes as possible is called bin packing, and W-02 does it to count the fewest nodes Fennel could manage with. The scheduler, by default, doesn’t. As §02 showed, it prefers the emptiest node and spreads copies out, which is safer for Pods but isn’t the cheapest arrangement. Packing tightly is a setting engineers can switch on, and some fully managed modes pack for you. Either way, the scheduler only places new Pods. It never moves running ones to empty a node, because Pods are replaced, not moved.

W-02’s idle bar splits the room Fennel rents but doesn’t use into two kinds. The first is room that no Pod has reserved, either because there are more nodes than the reservations need or because the room is stranded in pieces too small for any Pod. The second is room that Pods have reserved and don’t use, because their requests are bigger than the service needs. The “less than a third busy” on Ari’s dashboard counts both kinds together.

How common is this?

Two surveys give a rough sense, each from one source. One vendor’s dataset, Datadog’s State of Cloud Costs 2024, comes from organizations that use its cost tool on their AWS bills, and covers all containers on AWS machines, not only Kubernetes, from May 2023 to April 2024. It found that 83% of container spend went on idle room: about 54 points on room no Pod had reserved, and 29 on requests bigger than the workloads needed.

In a community survey by the CNCF, run from June to November 2023 with just over 100 self-selected respondents, 49% said Kubernetes had driven their cloud spend up. Over-provisioning, which means reserving more than workloads need, was by far the most-cited cause, named by 70%.

These are single surveys, not industry averages.

If you’re billed per Pod, the picture shifts, but the lesson stays the same. In most setups you pay for the machines; a few per-Pod options bill for what each Pod requests while it runs, not for what it uses. So padding costs money there too, Pod by Pod. And not every fully managed mode bills per Pod: some still bill per machine.

What does a per-Pod mode charge for, exactly?

On one provider, the per-Pod mode charges, per second, for the processor, memory and temporary disk space that each running Pod requests, not for what it uses. Pods that are waiting to be placed aren’t billed there, but Pods that keep crash-looping are. Another provider’s per-Pod option adds 256 MB to each Pod for Kubernetes’ own parts and rounds up to the next size it offers, so a Pod that requests 1 core and 8 GB is given, and billed for, 2 cores and 9 GB. Prices are the subject of Chapter 14.

So here is the answer to Morgan’s question, with the biggest cause first. Fennel rents two extra nodes because on Friday the teams’ padded requests had filled three nodes on paper, while the services were using far less. Next, node 06 has stayed nearly empty since Friday, which makes it a node’s worth of spare room; whether Fennel wants that spare is a choice, and the next section explains why it might. Last, on every node about 3 GB of the 16 GB machine is kept back for the system, where no Pod can reserve it, and Fennel pays for it anyway. The bill also has a small fee per cluster for the control plane, which Chapter 14 covers. Requests closer to what each service uses at its busiest would let Fennel rent fewer nodes, but not as few as possible, and §05 and §08 explain why.

§ 05 Room on purpose

Friday showed what a cluster with no spare room does on an ordinary busy evening: it leaves Pods waiting. Since 03:04, Fennel had been running on three nodes with almost nothing spare, and that missing room is what Chapter 4 said this chapter was about. If a node had died during the rush, its Pods would have been replaced, as they were at 03:04, but the replacements would have had nowhere to go, and they would have waited, as the dispatch Pod did.

Some unused room is therefore insurance, kept on purpose. A spare node’s worth of room lets the cluster place a lost node’s Pods straight away. Requests sized to a service’s busiest hour leave room unused for the rest of the week, and that is the point: the room is protected for the daily peak, as the documentation put it in §02. Chapter 3 called spare room insurance and left “how much?” to this chapter. The honest answer is that it’s a decision, which engineers and finance make together, and the spare-node switch in W-02 shows what it costs.

§ 06 Machines of different kinds: node pools

If orders keeps growing, a day may come when its request is bigger than the room any of Fennel’s nodes offers. The Kubernetes documentation is blunt about that case: a Pod larger than every node will never be placed, and W-02 shows it when you push orders past 13 GB. The answer is a bigger machine type, and a cluster can have more than one.

A node pool is a group of identical nodes within a cluster. Every node in a pool is the same machine type, and a pool is added, resized or removed as a whole. A cluster can have several pools of different machine types, such as a pool of large-memory machines for the Pods that need more memory than the general machines offer. (Some providers call them node groups.) The placement rules from §02 decide which Pods go to which pool.

Pools also let a team use cheaper machines. Spot machines are rented at a lower price, but the provider can take one back at short notice when it needs the capacity. Teams give them a pool of their own and send there only the work that can tolerate being interrupted.

§ 07 Tuesday: when a Pod uses too much

On Tuesday, Ari’s dashboard showed the orders Pod, orders-q2rw, with a restart count of 3. Its last state read Terminated · Reason: OOMKilled · Exit code: 137. Engineers will recognise the 137, but what matters for you is the word before it.

A manifest can hold a second number for each resource, and orders’ manifest does. Fig. 04 shows the section that sets both: what each copy reserves, its requests of 6 GB of memory, and the most it may use, its limits of 7 GB. A request isn’t a cap. A container may use more than it requested while its node has room to spare, and only a limit stops it. That second number is called the Pod’s limits.

New term · 03 / 04

limits

The most memory and processor a Pod’s container may use. They cap use; they reserve nothing.

The second number in Fig. 04.

Fig. 05 shows orders’ memory through Tuesday, against those two numbers.

Each time orders’ memory reached 7 GB, the operating system on the node stopped the container. Engineers say it was OOM-killed, from “out of memory”. The node agent then restarted the container, in the same Pod on the same node, so this was not a replacement like the ones at 03:04, and the restart count went up by one. Each restart left a short gap in which customers couldn’t place orders. If the kills keep coming, the node agent waits longer and longer between restarts, just as it did with Chapter 4’s crash-looping notifications.

New term · 04 / 04

OOM-killed

Stopped by the node’s operating system for going over its memory limit (“out of memory”), then restarted in place.

Engineers see OOMKilled, and exit code 137.

Processor works differently. A container that reaches its processor limit isn’t killed. Instead it is slowed down to its limit (engineers say throttled), because processor time is handed out in slices that can be held back, while memory a program is already holding can’t be taken away. So the symptom of a processor cap is “it got slow”, and the symptom of a memory cap is “it restarted”.

ANALOGYBack to budgets. If a request is the budget a project reserves, a limit is the spending cap on the project’s card. A project may spend beyond its reservation, up to its cap, while the department has money to spare.

WHERE THIS ANALOGY BREAKSReal spending caps work one way, but Kubernetes has two. The processor card never declines; it just slows the spending down. The memory card cuts the project off and starts it again from nothing. And spending above your reservation isn’t safe just because it’s allowed: when money runs short, the projects that are over their reservation are cut first, as §08 explains.

What if a team sets no memory limit at all?

Then nothing caps it. The container can use all the memory on its node, and if the node runs out, the Kubernetes documentation says a container with no limits is more likely to be the one killed. Leaving the limit off isn’t the safe choice: it lets one container put the whole node at risk.

§ 08 Using more than you reserved

Besides starting and restarting containers, as in Chapter 4, each node’s agent keeps an eye on how much memory its node has left. Ordinarily, Pods that use more than they reserved cause no trouble, because the node has room to spare.

If the node’s free memory falls too low, though, its agent removes Pods to protect the node and everything else running on it. That’s an eviction. The agent goes first for the Pods using the most memory beyond what they reserved, and Pods that stay within their requests go last. Unlike the kill in §07, an eviction removes the Pod itself. The ReplicaSet loop then writes a new Pod record, as it does for any Pod that disappears, and the scheduler has to place the replacement; on a full cluster, the replacement waits, as the dispatch Pod did on Friday. So a request set below what a service really uses doesn’t save that service any room. It puts the service first in line.

ANSWER“Is that a leak or real growth? And what does it do to our node count?”

If it’s a leak, a higher limit only delays the next kill; and if the request goes up too, Fennel rents room for a bug. If it’s real growth, a higher limit may be right, and the Kubernetes documentation’s advice is to check for a leak first, then raise the limit, “and possibly” the request.

Raising only the limit doesn’t change where Pods go. Raising the request does: each copy reserves more room, and on nodes that are already full, that can mean another node on the bill (try orders at 8 and then 12 GB in W-02).

If your question was “how much more memory?”, that’s the engineers’ number to work out. The two questions above decide whether more memory is the right fix, and what it costs.

In short

  • Each team writes down two numbers per service: what each copy reserves (its requests) and the most it may use (its limits).
  • The scheduler places each new Pod by its requests, memory and processor counted separately, on one node that has room for both. It never looks at how busy a node is.
  • If no node has room, the Pod waits, pending, and the scheduler keeps trying; nothing in this chapter makes room by itself.
  • Requests, packed onto nodes, decide how many machines you rent. Padding them buys nodes; cutting them below what services use buys evictions. Some spare room is insurance, on purpose.
  • At its memory limit a container is killed and restarted; at its processor limit it’s slowed. Before raising a limit, ask whether it’s a leak or real growth, and what it does to the node count.

Every loop so far has kept the same version of each service running.
